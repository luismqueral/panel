# Recipe: s3

Status: unverified. Written against `contracts.md`; the verification below has not been run. Say so to the person, and run it before calling the panel done.

## 1. When to use it

Uploads on a host with temporary disk, or many or large files. It fills the **files** contract.

## 2. Prerequisites

- An S3 bucket in `region`, and an IAM user or role that can only `s3:PutObject` on that bucket. Its keys in `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` on the server.
- `url`: the public base URL files are served from (the bucket's website endpoint, or a CDN in front of it).
- The project server.

## 3. Contract

Files, as in `contracts.md`. Keys `uploads/<yyyy>/<mm>/<8 random hex>-<safe name>`, the same naming as `local-disk`.

## 4. Steps

1. Write `server/s3.mjs` exporting `createS3({ bucket, region, url })` with `upload({ body, name, type })`, reusing the name, size, and type checks from `recipes/server/local-disk.mjs`.
2. Sign a `PUT https://<bucket>.s3.<region>.amazonaws.com/<key>` with AWS Signature Version 4 using `node:crypto` (HMAC-SHA256), or add the person's choice of AWS SDK to the project and say so.
3. Send `Content-Type` as checked, `x-amz-content-sha256`, and `Content-Disposition: inline`.
4. Return `{ url: <url>/<key>, name, size, type }`.
5. Configure the bucket or CDN to send `X-Content-Type-Options: nosniff`, and a sandboxing `Content-Security-Policy` for SVG.

## 5. Verify

- [ ] Upload an image: it shows in the field, and the object exists in the bucket.
- [ ] Reload: it still shows. Its URL opens directly.
- [ ] The IAM keys cannot list or delete objects.
- [ ] An HTML upload is refused.

## 6. Pitfalls

- Uploading from the browser with long-lived keys. Keys stay on the server.
- A bucket policy that allows public writes.
- Serving SVG from the site's own origin without a sandboxing CSP.
